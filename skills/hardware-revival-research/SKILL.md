# Hardware revival research

Use when building or refreshing a directory of old-device reuse, firmware, cloud replacement, or AI-assisted repair projects.

## Workflow

1. Define public scope and separate the intended repository from unrelated workspace files. Assign one writing/publishing owner; multiple monitoring chats are not multiple authors.
2. Discover by device and intended use. Prefer upstream repositories, compatibility tables, original tutorials and author posts. Treat search snippets as leads.
3. Read real content. Record model, hardware revision, firmware, region and required tools. Distinguish installing an app, replacing firmware, replacing a board, replacing cloud services and repairing physical damage.
4. Classify AI honestly: functionality, documented AI-assisted development/setup, adjacent display, or traditional infrastructure. No AI claim without a source.
5. Preserve stable IDs and family relationships. Mark tools/platforms separately from completed case routes. Use null/UNKNOWN for missing values, never invented zero costs. Keep three denominators explicit: unique project repositories, reviewed projects, and device/community routes.
6. Record E0 (discovery only), E1 (deployment docs read), E2 (specific author hardware claim), and E3 (independent reproduction verified). A repository API response or readable README entry point is E0, not compatibility review. None implies firsthand testing.
7. Verify maintenance and licenses. Distinguish archive, deprecation, mirror migration and historical patched methods. No recent push guarantee. Keep full upstream snapshots outside the public repo.
8. Write case analyses with before/after, fit/nonfit, prerequisites, limitations, cost components, recovery and proposed acceptance steps. Label unexecuted tests.
9. Build static detail pages and filterable navigation from the same data. Include actual downloads, canonical URLs and sitemap. Validate schema, IDs, sources, exports and local links.
10. Test rendered search, filter combinations, no-results, reset, URL persistence, details and downloads. Check desktop and narrow viewport separately.
11. Publish only within the user's authorized destination. Read back repository and deployed data independently, verify rendered public UI, and record limitations. No social messaging or automatic schedule unless requested.
12. Complete a three-level retrospective: deliverable quality, process failures/corrections, reusable mechanism. Keep private operational context outside public deliverables.

## Repository discovery gate

For a large project-source expansion, query the repository API and README instead of copying search results. Canonicalize owner/repository URLs, reject forks, 404s, profile repositories, obvious mirrors and migrated read-only copies, then deduplicate against the reviewed catalog and every parallel research batch. Store description, archive state, last push, default branch, API license identifier, check time and bilingual scope/use summaries. Publish these rows as E0 until installation, exact-model compatibility and recovery sources are reviewed item by item.

## Independent five-dimension revival stars

Keep the 1–5 revival-value stars independent from E0–E3. Score five raw dimensions from 1–5: feasibility/ease (easier is higher), expected cost (lower is higher), documentation/community activity, practical value, and bricking/security risk (lower is higher). Publish explicit base weights totaling 100%. When at least three dimensions have source-backed scores, proportionally renormalize only those dimensions' original weights to 100%, calculate the weighted average, and round to the nearest 0.5 star with exact ties upward. Evidence level never enters or caps the arithmetic.

Do not invent numeric facts from prose. If a dimension lacks a verifiable source, store its score, basis, and effective weight as `null` and its source list as empty; never impute a neutral 3. With fewer than three evidenced dimensions, publish no total or weighted average and use the exact localized labels `待评分 / Not yet rated`. Repository-metadata discoveries remain E0, provisional, and `needs_review: true` until installation, exact-device compatibility, rollback, and safety sources are reviewed item by item. Separate scoring research may produce a rating but does not upgrade E0–E3. Recent pushes may inform only the docs/community dimension and never prove hardware support.

Every public row must expose five nullable raw scores, per-dimension bilingual basis and source URLs, evidenced-dimension count, effective weights, nullable weighted average and half-star total, independent evidence level, review-needed state, source URL, and stable bilingual detail URLs in the unified JSON/CSV. Keep a canonical scoring-evidence ledger for manually enriched entries. Validate base weights totaling 100%, the three-dimension threshold, proportional renormalization, score recomputation, all nine half-star buckets, rated/unrated counts, JSON/CSV/source-ledger parity, independent star/evidence filtering, rated-first default sorting, and exact bilingual unrated/review markers. Keep project-source downloads separate from the full route export so users can see which denominator they are using.

## Update discipline

Metadata refresh is not content review. Read changed documents before refreshing editorial review dates or upgrading evidence. Keep version, sitemap, JSON/CSV exports, report counts, browser tests and build artifacts consistent. Use the issue forms for exact model-level success and failure reports.

For a display-only simplification, preserve every source row and every JSON/CSV field. Move secondary facts from compact cards to stable detail pages instead of deleting them; keep core search, score/evidence filters, default sorting, canonical URLs, and narrow-screen access. Before release, compare entry counts and export parity with the baseline, bump all coordinated version fields, rebuild the sitemap, and verify both rendered languages and the deployed artifact independently.

For a compact site-wide footer, keep one localized line with only stable navigation or license links. Put release version, review dates, hands-on-testing boundaries, and the complete export inventory on an About or download section instead of repeating them on every page. Audit every generated footer for exact link count, order, labels, targets, and absence of old metadata; render-check the longest language at 390 px for one-line fit and zero horizontal overflow. Re-audit every generated list card at the same release gate so footer work cannot reintroduce hidden card fields.

For a minimal directory shell, make the visible-control contract explicit and test it in every language: one search field, the approved primary filters, and at most one small methodology link. Retiring a filter means removing its markup and JavaScript behavior, cleaning obsolete query parameters, and proving those parameters no longer hide records. Count every control, including icon links, when checking row wrapping. At the narrow-screen gate, assert form/document widths and a maximum first-card vertical position so a technically responsive header cannot push the actual directory below the useful first viewport.

For a generated project-page visual pilot, keep the pilot IDs and any finalized SEO or editorial overrides in tracked source data. Gate the new renderer to those IDs and current canonical pages so a full deterministic rebuild leaves non-pilot and historical pages byte-stable. Reuse the site's purpose, snapshot, score, spec, media, hardware-tag, link, and source components; add only the layout and state classes the pilot cannot express. Before committing, compare finalized title, description, canonical, hreflang, Open Graph fields, and protected editorial fragments against `HEAD` exactly; separately allow the intended stylesheet cache-key change. Render every pilot language at a desktop and narrow viewport, checking hero order, chip wrapping, image/placeholder behavior, no lazy-loaded hero, zero horizontal overflow, console warnings, and the complete repository validator.

For an AI-retrofit landing page, frame the product around the exact hardware already owned, not around generic AI capability. Derive route counts, evidence labels, summaries, model scope, and modification methods from canonical catalog data; never duplicate compatibility claims in freehand landing copy. Make the first action a device/model search, then show a small set of traceable route entry points and three explicit gates: exact-model match, what the source actually proves, and when to stop. A visual may explain the retrofit chain (device, bridge/board/service, outcome), but must not imply local inference, universal compatibility, a verified build, or known cost. Keep all new styles homepage-scoped, preserve the existing search and category contracts, rebuild both languages, run repository validation, and render-check desktop plus 390 px for overflow, reading order, working links, and console errors. Run the existing browser contract unchanged; keep compact homepage copy within its one-line desktop and mobile limits rather than weakening assertions. Branch work does not authorize Pages, merge, or deployment.

For an AI-retrofit decision guide, identify the exact hardware generation and diagram the real compute boundary before comparing routes. Keep service bridging, OEM-firmware modification, replacement firmware, and replacement PCB distinct even when an upstream summary uses “jailbreak.” State whether ASR, LLM, and TTS run on the endpoint, a LAN host, or an optional cloud service. Present at least one stop route beside build routes, preserve original-feature losses and rollback limits, and separate reviewed repository routes from GitHub-index-only leads. A repository or demo is not hands-on reproduction; unknown cost, latency, power, and long-term stability stay unknown.

For a static directory that must remain globally searchable, paginate the generated HTML into canonical, reciprocal-hreflang pages and include every page in the sitemap. Keep the unfiltered document limited to its own page; only when search or filters are active, fetch the other static pages, import their cards, and resolve every relative link against the source page before insertion. Hide pagination during the global result view and restore the page-local view when filters clear. Static validation must aggregate card counts, evidence markers, internal links, canonicals, and sitemap coverage across all pages. Browser acceptance must cover a deep page, cross-page query/filter counts, reload and URL state, normalized card targets, console errors, and 390 px overflow.

When a landing-page label names a canonical class such as reviewed AI functionality, link to an explicit facet (`?ai=native`) rather than a keyword query (`?q=AI`). Carry the facet through generated card metadata, a visible localized control, URL restoration and cleanup, active-filter detection, cross-page loading, and composition with every existing primary filter. Before release, record the keyword baseline and structured-facet result counts, assert every structured result has the exact canonical value, click the landing entry in a browser, reload the filtered URL, and repeat at 390 px. Treat a changed control count or wrapped-row count as an intentional UI-contract change that must update static and browser assertions without weakening overflow or first-card-position gates.

## Unpublished tutorials and search-discovery audits

Keep community post drafts outside the publication tree in an explicitly ignored `drafts/` directory. Use one Markdown file per route with a Chinese-first audience, prerequisites, rough steps, stop conditions, source boundary, and short English summary. Link the stable KitAgain detail page and direct upstream setup, compatibility, safety, or recovery documents; label the text as an unpublished editorial draft and never imply hands-on testing. Before handoff, check every linked URL, strict UTF-8 decoding, `git check-ignore`, and an empty `git ls-files -- drafts` result. Draft creation never authorizes posting.

For a Search Console readiness audit, validate the generated and deployed artifacts separately. Parse the sitemap, check its schema namespace, UTF-8 encoding, URL and byte limits, unique absolute HTTPS canonical-host URLs, and W3C `lastmod` values. Fetch every sitemap URL without following redirects and reject non-200 responses, `noindex`, mismatched self-canonicals, or broken hreflang clusters. Every localized page must list itself and every alternate, each pair must return-link, and `x-default` must be a real fallback inside that content cluster rather than an unrelated global page. Read back root `robots.txt`, require an absolute `Sitemap:` line, and reject accidental blocking rules. Fix only demonstrated technical errors, rebuild deterministically, rerun the full audit after deployment, and keep any owner submission checklist uncommitted when requested.

## Evidence-enrichment releases

Keep each research round in an append-only batch ledger before merging it into canonical data. Retain attempted entries that fail the three-dimension scoring gate, with unproved dimensions as literal `null`; report attempted, qualified, and still-unrated counts separately. Validate that every non-null dimension has bilingual reasoning, at least one direct HTTPS source, and an access date. Search-result snippets are discovery aids, not scoring evidence.

Treat cost as a two-part evidence gate: a used-device price range plus the complete modification input (parts and required tools). Score cost only when both halves have cited ranges and access dates. Open-source software being free does not establish zero modification cost, and a parts price without the host/device price is not a complete cost basis. Publish explicit null reasons and count both filled and lacking-source records.

For a deep audit of E0 discoveries, preserve every original row and stable ID. Record one of four outcomes with sources: upgrade to E1, upgrade to E2, stay E0, or reject from display while retaining the record in machine-readable exports. A delisted entry must disappear from cards, detail generation, and sitemap, while remaining in JSON/CSV with `display_status`, audit rationale, sources, and a null public detail URL. Recompute evidence and review-needed counts from data instead of carrying old constants.

For every listed route whose final score is at least 4, render exactly three compact bilingual action blocks: what is needed, rough steps, and when to stop. Each block needs one or more upstream tutorial, compatibility, or recovery links. Store the same structure in exports, validate every qualifying detail page in both languages, and ensure lower-rated, unrated, or delisted entries do not receive the block by accident.

Action blocks must describe entry-specific prerequisites, operations, and stop conditions, not scoring rationale or title-substituted boilerplate. Do not infer firmware images, model matching, backup tools, or flashing steps for a software-only route. When the scoring ledger is too abstract to support a useful guide, add a reviewed manual guide to the canonical record and cite the exact upstream setup, compatibility, security, or recovery page behind each block. Exclude commit feeds, release/history pages, changelogs, search/results pages, and marketplace listings from tutorial links. At validation time, normalize entry titles before comparing whole guides and reject repeated blocks or guides that remain identical after normalization.
