# Hardware revival research

Use when building or refreshing a directory of old-device reuse, firmware, cloud replacement, or AI-assisted repair projects.

## Workflow

1. Define public scope and separate the intended repository from unrelated workspace files. Assign one writing/publishing owner; multiple monitoring chats are not multiple authors.
2. Discover by device and intended use. Prefer upstream repositories, compatibility tables, original tutorials and author posts. Treat search snippets as leads.
3. Read real content. Record model, hardware revision, firmware, region and required tools. Distinguish installing an app, replacing firmware, replacing a board, replacing cloud services and repairing physical damage.
4. Classify AI honestly: functionality, documented AI-assisted development/setup, adjacent display, or traditional infrastructure. No AI claim without a source.
5. Preserve stable IDs and family relationships. Mark tools/platforms separately from completed case routes. Use null/UNKNOWN for missing values, never invented zero costs. Keep three denominators explicit: unique project repositories, reviewed projects, and device/community routes.
6. Record E0 (discovery only), E1 (deployment docs read), E2 (specific author hardware claim), and E3 (independent reproduction verified). A repository API response or readable README entry point is E0, not compatibility review. None implies firsthand testing.
7. Verify maintenance and licenses. Distinguish archive, deprecation, mirror migration and historical patched methods. No recent push guarantee. Keep full upstream snapshots outside the public repo.
8. Write case analyses with before/after, fit/nonfit, prerequisites, limitations, cost components, recovery and proposed acceptance steps. Label unexecuted tests.
9. Build static detail pages and filterable navigation from the same data. Include actual downloads, canonical URLs and sitemap. Validate schema, IDs, sources, exports and local links.
10. Test rendered search, filter combinations, no-results, reset, URL persistence, details and downloads. Check desktop and narrow viewport separately.
11. Publish only within the user's authorized destination. Read back repository and deployed data independently, verify rendered public UI, and record limitations. No social messaging or automatic schedule unless requested.
12. Complete a three-level retrospective: deliverable quality, process failures/corrections, reusable mechanism. Keep private operational context outside public deliverables.

## Repository discovery gate

For a large project-source expansion, query the repository API and README instead of copying search results. Canonicalize owner/repository URLs, reject forks, 404s, profile repositories, obvious mirrors and migrated read-only copies, then deduplicate against the reviewed catalog and every parallel research batch. Store description, archive state, last push, default branch, API license identifier, check time and bilingual scope/use summaries. Publish these rows as E0 until installation, exact-model compatibility and recovery sources are reviewed item by item.

## Independent five-dimension revival stars

Keep the 1–5 revival-value stars independent from E0–E3. Score five raw dimensions from 1–5: feasibility/ease (easier is higher), expected cost (lower is higher), documentation/community activity, practical value, and bricking/security risk (lower is higher). Publish explicit weights totaling 100%, calculate the weighted average, and round to the nearest 0.5 star with exact ties upward. Evidence level never enters or caps the arithmetic.

Do not invent numeric facts from prose. If comparable structured facts are unavailable, use an explicitly disclosed neutral placeholder and record its basis as `unknown-neutral` or `unreviewed-neutral`; a neutral 3 is not proof of average performance. Repository-metadata discoveries remain E0, provisional, and `needs_review: true` until installation, exact-device compatibility, rollback, and safety sources are reviewed item by item. Recent pushes may inform only the docs/community dimension and never prove hardware support.

Every public row must expose the five raw scores, per-dimension basis, weighted average, half-star total, independent evidence level, review-needed state, source URL, and stable bilingual detail URLs in the unified JSON/CSV. Validate 100% coverage, weights totaling 100%, score recomputation, all nine half-star buckets, JSON/CSV parity, independent star/evidence filtering, default star-desc sorting, and rendered review markers. Keep project-source downloads separate from the full route export so users can see which denominator they are using.

## Update discipline

Metadata refresh is not content review. Read changed documents before refreshing editorial review dates or upgrading evidence. Keep version, sitemap, JSON/CSV exports, report counts, browser tests and build artifacts consistent. Use the issue forms for exact model-level success and failure reports.
